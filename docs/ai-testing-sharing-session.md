> **AI 最适合做的，不是替你做决定，而是帮你把测试里重复、耗时、格式化的部分加速掉；关键判断仍然要人来做。**

### 【痛点 — 3 分钟】

（切屏：痛点页）

做测试的同事应该都有同感，我日常最耗时间的其实是四件事：

**第一，测试设计。** 每个版本都有新需求，产品文档、飞书 Wiki、口头补充规则混在一起。拆成 Excel 用例、标优先级、补边界场景，经常要半天甚至一天。

**第二，自动化起步慢。** 接口文档有了，但要写 client、写 fixture、写断言、处理登录 token，样板代码很多。UI 还要处理登录、滑块、页面定位，第一版框架往往要磨很久。

**第三，回归成本高。** 用例写完了，如果只能手工点一遍，版本一多就回归不过来。需要能一键跑、能出报告、失败了能快速定位。

**第四，协作摩擦。** 产品关心「测没测到」，开发关心「是不是环境问题」，测试夹在中间，如果没有结构化产物——用例表、日志、截图、接口请求响应——沟通成本很高。

（停顿）

我尝试过几种方式：纯 ChatGPT 网页问答、Copilot 补全、最后主力落到 **Cursor**——因为它能读整个仓库、改多个文件、跑终端命令，还能接 MCP 工具。对我来说，差别不是「会不会写代码」，而是 **能不能把 AI 嵌进工程上下文**。

### 【我的工具栈 — 3 分钟】

（切屏：工具栈页）

我现在的组合很简单，就三层：

**第一层：Cursor IDE。** 这是我的主战场。项目代码在 `Pyautotest` 里，技术栈是 `Playwright + Pytest + Allure`，覆盖 CRM 接口、商城 UI 巡检、移动端 Monkey / Appium 探索。

**第二层：项目规则与上下文。** 我会让 AI 先读现有代码再改——比如 `api/client.py` 怎么封装、`conftest.py` 里登录 fixture 怎么用、Allure 怎么 attach 请求响应。这样生成出来的代码风格和项目一致，而不是每次从零写一套。

**第三层：MCP 扩展。** 我试过 TestSprite，用 MCP 让 AI 能生成测试计划、尝试执行。实话说，它对本地服务的项目更友好；我们 CRM 打的是远程 staging 环境，所以最终还是要和现有 pytest 结合。这个后面案例里会讲到。

（停顿）

对产品同事：你们可以把它理解成「一个读过我们项目文档、能帮忙出用例初稿和检查清单的助手」。

对开发同事：你们可以把它理解成「能快速写测试样板、补异常场景，但断言和业务规则我会 review 的协作方」。

### 【案例一：需求 → 结构化用例 → Excel / XMind — 6 分钟】

（切屏：用例生成链路图）

这是我用得最多、也最容易让产品同事有共鸣的一段。

以 CRM 需求为例，比如 CRM3.13 优化、客户基础信息优化、线索看板、企微对接等。传统做法是：读完需求文档，手工填 Excel。

我现在的方式是 **「结构化一次，多处复用」**：

1. 把需求拆成模块、场景、优先级、是否阻塞、前置条件、步骤、预期结果
2. 写进 Python 数据文件，比如 `cases_crm313.py`
3. 跑生成脚本 `generate_crm313_test_artifacts.py`
4. 自动产出 `testcases/CRM3.13_Optimization_TestCases.xlsx` 和 `.xmind` 脑图

（停顿）

这个模式我已经复用了至少 9 个需求模块，包括：CRM3.13、CRM0403、线索看板、客户跟进看板、企微、小程序询盘、UB 绑定、易食包微信注册、创建编辑客户线索等。

**AI 在这里具体帮什么？**

- 根据需求描述，补全边界用例：比如「已绑定外呼手机号才显示解绑按钮」「未绑定不显示」「二次确认弹窗文案要带真实号码」
- 统一用例格式：用例 ID、P0/P1、首轮必测、阻塞标记
- 快速扩写：一个功能点从 3 条扩到 10 条，我再删改，而不是从 0 写

**人必须做什么？**

- 业务规则对不对——这是产品最该帮我把关的
- 优先级是否合理
- 有没有遗漏跨模块场景，比如权限、数据联动、异常回滚

（停顿）

这里有个很重要的原则：**AI 出初稿，人做 sign-off。** 我不会把 AI 生成的用例直接当最终版发给全组，一定会过一遍。但时间从「写」变成了「审」，效率差很多。

对产品同事的建议：如果你们需求文档里模块、规则、异常说明写清楚，测试用 AI 扩用例的质量会高很多。模糊需求 → AI 也会模糊。

### 【案例二：用例 → 自动化代码 — 6 分钟】

（切屏：自动化架构简图）

第二层是把能自动化的部分变成代码。我项目里目前几块：

**CRM 接口自动化（核心）**

- 7 个 API 测试文件，覆盖：创建线索、认领、分配、移公海、活动记录、组合流程
- `test_api_negative.py` 里有 11 条异常场景：错误密码、无 token、缺字段、非法分页、空 ID 等
- 使用 `api/client.py` + `api/services/` 分层，登录 token 通过 fixture 复用
- 每条用例用 Allure 附加 request/response JSON，失败好定位

**商城 UI 巡检**

- 易食包生产环境：`test_esbao_mall_ui.py`，登录 → 进商城 → 滚首页 → 点热销商品 → 校验详情
- ePak 英文商城：`test_epak_mall_ui.py`
- 每次产出截图 + `report.json`，支持邮件报告

**移动端**

- Monkey 稳定性：自动装 APK、分段截图、白屏检测
- Appium 随机探索：只点应用内可点击元素，比纯 Monkey 更可控

（停顿）

**AI 在这里帮什么？**

- 按接口文档生成 service 方法和 pytest 用例骨架
- 批量补 negative case——这类用例格式固定，特别适合 AI
- Page Object：登录页、商城首页、详情页的定位和步骤
- Jenkinsfile、bat 脚本、邮件报告配置——运维型样板代码

**我必须盯什么？**

- 鉴权与环境：token 怎么传、加密密码怎么处理
- 断言是不是业务真相：比如 CRM 成功是 `code=1000`，失败场景不能误报成功
- 测试数据：随机手机号、国家联动、线索 ID 要不要清理
- Flaky 用例：UI 等待、滑块验证码——我有自动重试和人工接管 120 秒

（停顿）

对开发同事：如果你们接口返回结构稳定、错误码文档齐全，测试用 AI 扩异常用例会非常快。反过来，如果错误码不一致或环境数据经常变，AI 写得再快也维护不起来——**自动化维护成本取决于接口和环境的稳定性，不取决于 AI**。

### 【案例三：本地 → Jenkins 定时回归 — 3 分钟】

（切屏：CI 流水线页）

自动化只有能在 CI 里跑，才算团队资产。

我现在有几条流水线：

- **CRM API 回归**：`scripts/run_crm_api_jenkins.bat`，支持 `INCLUDE_NEGATIVE` 开关，产出 JUnit + 可选邮件
- **易食包 UI 巡检**：`Jenkinsfile.esbao-ui`，每 30 分钟触发，归档截图
- **ePak UI、Monkey、外呼保活**：各有独立 Jenkinsfile 和文档

本地和 Jenkins 用同一套脚本，避免「我机器上能跑，CI 上不行」。

AI 在这里主要帮我写 Groovy 流水线、排错文档——比如 GitHub 拉不下来时，我做了 `Jenkinsfile.crm-api.stable`，用本机目录 + `SKIP_GIT_SYNC`，这在 `docs/jenkins-crm-api-setup.md` 里有完整说明。

（停顿）

分享一个真实结果：`reports/test-summary-last.json` 会记录每次执行耗时、通过失败数；UI 报告在 `reports/ui/esbao/` 和 `reports/ui/epak/` 带时间戳目录。失败了有截图、有 JSON、有 Allure，跟开发对线时省很多口舌。

### 【踩坑与原则 — 2 分钟】

（切屏：原则页）

最后讲实话——哪些地方 AI 帮不上，或者会帮倒忙。

**坑 1：幻觉。** 它可能编造不存在的接口字段、错误的 CSS 选择器。对策：让它读现有文件再改；改完必须跑 pytest。

**坑 2：一次改太多。** 早期我让它「帮我把 CRM 全测一遍」，结果 diff 巨大，review 不动。对策：**小步迭代**，一次一个文件、一个场景。

**坑 3：盲目信任工具报告。** TestSprite 曾因为检测本地 443 端口失败而阻塞，但我们的 API 在远程 staging。对策：**工具输出要和人写的 pytest 交叉验证**。

**坑 4：把敏感信息写进 prompt。** 账号密码走 `.env` 和 Jenkins Credentials，不进 Git，不贴进对话。

（停顿）

我总结四条原则：

1. **AI 写初稿，人做 sign-off**
2. **给足上下文**（项目结构、现有代码、接口文档）
3. **小步提交、立即运行**
4. **能模板化的先模板化**（用例生成脚本、negative 用例、报告格式）

### 【收尾 — 2 分钟】

（切屏：行动清单页）

如果各位想下周就开始试，我给三条最低成本建议：

**测试同事：** 挑一个即将上线的需求，把模块和规则整理成结构化列表，让 AI 补 10 条边界用例，你再删到 5 条真正有价值的。

**开发同事：** 新接口上线时，顺手要 AI 根据 OpenAPI / 接口说明生成 3 条异常用例 PR，测试 review 后并入回归。

**产品同事：** 需求评审时多写「不做什么、异常时怎样」——这会直接提升 AI 辅助出用例的质量。

（停顿）

我的体会是：AI 没有让我变懒，而是让我把精力放在**判断测什么、什么算通过、怎么让团队看见质量**上。重复劳动交给 AI 和脚本，这才是测试落地该走的路。

### 第 15 页 — 四个坑

**标题：** 我踩过的坑

**要点：**
1. 幻觉 — 编造字段/选择器
2. 一次改太多 — diff 无法 review
3. 盲信工具报告 — 环境不匹配

### 步骤 A — Cursor 里让 AI 补一条异常用例（2 分钟）

**1. 打开文件**

```
tests/test_api_negative.py
```

**2. 选中一个已有用例**（如 `test_login_wrong_password`），让观众看到结构。

**3. 在 Cursor Chat 输入以下 prompt（可提前贴到记事本，现场粘贴）：**

```
请阅读 tests/test_api_negative.py 和同目录下其他 API 测试的写法。
仿照现有风格，新增一条异常用例：
- 场景：登录时账号为空格字符串 "   "
- 预期：登录失败，code 不等于 1000
- 使用 allure feature/story/title 注解
- 使用 _attach_api_detail 附加请求响应
- 不要改其他用例
只修改 tests/test_api_negative.py，改完后告诉我函数名。
```

**4. 展示 AI 生成的 diff**（停顿 10 秒让观众看）

**5. 口头强调：**
- 「我给了现有文件作模板，所以风格统一」
- 「我只让它改一个文件，方便 review」

**6. Accept 合并代码。**

> **备用：** 若现场 AI 慢或失败，提前准备好已添加的用例分支，直接展示 diff 并说「这是今早预演生成的」。

---

### 步骤 B — 终端运行 pytest（1 分钟）

**1. 打开终端，执行：**

```powershell
cd E:\cursor\Pyautotest
python -m pytest tests/test_api_negative.py::test_login_whitespace_account -v --tb=short
```

> 函数名按 AI 实际生成的为准；预演时记下正确名字。

**2. 若只想快演示，跑已有稳定用例：**

```powershell
python -m pytest tests/test_api_negative.py::test_login_wrong_password -v --tb=short
```

**3. 口头解说：**
- `-v` 看每条结果
- 失败时 `--tb=short` 看关键栈
- 全量 CRM API 回归用 `.\scripts\run_crm_api_jenkins.bat`

## 四、Q&A 预判（备用）

| 问题 | 参考回答 |
|------|----------|
| 你用什么 AI？ | 主力 Cursor；核心是「能读项目、能跑命令」，不是某个固定模型 |
| 要学编程吗？ | 不必成为开发，但要能读 pytest 失败、会审 diff、会跑命令 |
| 会不会泄密？ | 账号密码放 .env / Jenkins Credentials；不把生产密钥贴进对话 |
| 产品怎么参与？ | 需求写清规则与异常；评审 AI 生成的用例初稿 |
| 开发怎么参与？ | 提供稳定接口契约；接受测试提交的异常场景 PR |
| 投入产出比？ | 用例生成和 negative 用例 ROI 最高；UI 需持续维护定位 |
| 没有 Cursor 行吗？ | 可以，把「给上下文、小步、运行验证」迁到 Copilot/ChatGPT 也行，效率低一些 |
