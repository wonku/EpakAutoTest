# 飞书需求 → 固定格式用例

## 何时使用

用户给出飞书文档地址（`feishu.cn` / `larksuite.com` 的 `wiki` / `docx` / `docs`），并要求生成测试用例到某目录时，必须按本 Skill 执行。

## 输入

| 项 | 规则 |
|----|------|
| 飞书 URL | 必填。支持知识库 Wiki、新版文档 docx |
| 关联飞书 URL | 可选。一个版本需求分散在多个文档时，合并阅读后更新同一份用例 |
| 输出目录 | 用户指定优先；未指定则用本仓库 `testcases/` |
| 需求简称 | 用户指定优先；否则从文档标题提炼，用于文件名（中文或英文均可） |
| 更新模式 | 用户要求“合并/更新/补充”时，优先读取已生成 Excel 或生成脚本，在原产物上增量更新 |

## 输出文件（固定命名）

在输出目录生成两份：

```
{需求简称}_TestCases.xlsx
{需求简称}_TestMindMap.xmind
```

示例：`CRM支持创建新版询价单_TestCases.xlsx`、`CRM支持创建新版询价单_TestMindMap.xmind`

不要改列名、不要省略 XMind，除非用户明确只要其中一种。

## 工作流

复制进度并逐项完成：

```
Task Progress:
- [ ] 1. 解析 URL，拉取飞书正文
- [ ] 2. 若为更新模式，读取已生成用例并识别现有覆盖
- [ ] 3. 拆需求点 / 模块，标优先级与阻塞
- [ ] 4. 按固定字段新增或修订用例
- [ ] 5. 生成 Excel（含固定 Sheet）
- [ ] 6. 生成 XMind
- [ ] 7. 回传路径、覆盖摘要、增量说明
```

### 1. 拉取飞书正文（优先 MCP）

使用 MCP 服务器 `user-lark-mcp`：

1. **Wiki URL**（路径含 `/wiki/{token}`）：
   - 调用 `wiki_v2_space_getNode`，`params.token` = wiki token
   - 从返回中取实际文档 `obj_token` / `obj_type`
   - 若为 docx：再调 `docx_v1_document_rawContent`，`path.document_id` = obj_token
2. **Docx URL**（路径含 `/docx/{token}`）：
   - 直接 `docx_v1_document_rawContent`，`document_id` = docx token
3. 需要用户身份时设 `useUAT: true`

权限失败时：请用户粘贴全文或放到 `specs/`，再继续生成；不要编造需求内容。

详细 token 规则见 [feishu-fetch.md](feishu-fetch.md)。

### 多文档与更新已生成用例

当用户提供多个飞书文档，或明确说“合并到上面生成的用例”“更新需求后更新用例”：

1. 先读取所有主文档、关联文档、字段表说明和讲解资料。
2. 判断文档关系：
   - 主 PRD：定义功能主流程、入口、导出/提交行为。
   - 关联 PRD：定义字段、后台页面、兼容逻辑、上下游取数。
   - 讲解资料：用于补全测试点和待确认项，不单独生成新文件。
3. 优先更新上一份同主题产物：
   - 若有生成脚本，更新脚本并重新生成。
   - 若只有 Excel/XMind，读取现有用例后增量补充 Sheet 和用例。
4. 不重复已有等价用例；新增用例 ID 使用新模块前缀或当前模块后续序号。
5. 在「需求追溯」写入所有文档 URL；在「覆盖检查」标出新增覆盖和待确认点。
6. 若关联文档引用的表格/附件无法读取（如 sheet MCP 不可用），不要臆造具体字段；先按可确定的字段类型、必填性、格式、联动、展示、导入、兼容范围补用例，并在备注标注“待以 <表名> 核对”。

### 2. 拆解需求

从正文提取可测需求点，按模块分组。忽略纯排期、人员、无关历史。

每个需求点至少覆盖：

| 类型 | 优先级建议 | 是否阻塞 | 首轮必测 |
|------|------------|----------|----------|
| 主流程成功 | P0 | 入口/权限/核心数据类为「是」 | 是 |
| 校验/异常/边界 | P1 | 否 | 视核心度 |
| 权限/显隐/越权 | P1 | 菜单/数据权限基线可为「是」 | 视情况 |
| 兼容/体验/非关键 | P2 | 否 | 否 |

口径冲突或文档写不清处：在「备注」写「待产品确认：…」，不要静默假设。

### 3. 固定用例字段（Excel 行）

每条用例必须使用以下列（顺序固定）：

```
用例ID | 模块 | 优先级 | 场景 | 前置条件 | 测试步骤 | 预期结果 | 实际结果 | 备注 | 用例状态 | 是否阻塞 | 首轮必测
```

| 列 | 取值约定 |
|----|----------|
| 用例ID | `{模块前缀}-{三位序号}`，如 `IQ-001`；同模块连续编号 |
| 模块 | `序号-模块名`，如 `1-询价记录Tab` |
| 优先级 | 仅 `P0` / `P1` / `P2` |
| 场景 | 一句可执行标题，含动作+对象 |
| 前置条件 | 环境、账号、数据、开关 |
| 测试步骤 | 编号步骤 `1. …\n2. …` |
| 预期结果 | 可判定的结果，勿写「正常」 |
| 实际结果 | 留空 |
| 备注 | 需求原文摘录 / 待确认项 |
| 用例状态 | 留空（Sheet 内下拉：PASS/FAIL/BLOCK/N/A） |
| 是否阻塞 | `是` / `否` |
| 首轮必测 | `是` / `否` |

完整 Sheet 与样式约定见 [case-format.md](case-format.md)。可参考仓库现有生成脚本风格（如 `generate_crm313_test_artifacts.py`）。

### 4. Excel Sheet 结构（固定）

| Sheet | 用途 |
|-------|------|
| 需求追溯 | 飞书 URL、文档标题、范围摘要、统计（合计/阻塞/首轮/P0） |
| 总测试用例 | 全部用例，表头为上述 12 列 |
| 按模块分 Sheet | 每个模块一张（名称 ≤31 字，去掉 `\ / ? * [ ]`） |
| 首轮冒烟 | `首轮必测=是` |
| 阻塞场景清单 | `是否阻塞=是`：用例ID、模块、场景、优先级、阻塞说明、失败影响 |
| 优先级说明 | P0/P1/P2、阻塞、首轮、状态含义 |
| 覆盖检查 | 需求点、覆盖情况、对应用例ID |

「用例状态」列加数据校验下拉：`PASS,FAIL,BLOCK,N/A`。阻塞行浅红底，P0 行浅蓝底（与现有 CRM 用例一致）。

### 5. XMind

根节点：`{需求简称} 测试脑图`  
一级：模块 → 二级：`{用例ID} {场景}`（可再挂优先级/阻塞标签）。

用 zip + `content.json` / `manifest.json` / `metadata.json` 生成（与仓库现有 XMind 生成方式一致）。

### 6. 完成后回复

只报告：

1. 输出文件绝对路径  
2. 用例总数、P0/阻塞/首轮数量  
3. 模块列表与覆盖缺口 / 待确认项（若有）

## 质量底线

- 不得脱离飞书正文臆造业务规则  
- 步骤与预期必须可执行、可判定  
- 列名与 Sheet 集合保持固定，便于后续回归与导入  
- 用户指定目录不存在时先创建再写入
